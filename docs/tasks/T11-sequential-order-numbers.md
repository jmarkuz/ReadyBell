# T11. Послідовні номери замовлень для ресторану (BACKLOG F1)

| Поле | Значення |
|------|----------|
| Пріоритет | P2 (хвиля 3) |
| Розмір | M |
| Статус | Todo |
| Впливає на | T01 (пошук / сортування за номером), T12 |

## Проблема
Номер замовлення — перші 8 hex-символів UUID (`#3F9A21C0`): нечитабельний, не гарантовано унікальний, не послідовний.
Для каси й клієнтів потрібен `#101`.

## Обсяг
- Поле `order_number` (int) на `Order`, унікальне в межах `(tenant_id)`; лічильник на ресторан (рядок-лічильник з `SELECT … FOR UPDATE` або sequence на tenant).
- Міграція з бекфілом наявних замовлень за `created_at`.
- API (`orderId` у відповідях), receipt, push-текст `OrderReadyHandler`, пошук і сортування `ORDER_ID` — на новий номер.
- Політика скидання (щодня / ніколи) — рішення власника продукту; за замовчуванням не скидати.

## Критерії приймання
- [ ] Паралельне створення 50 замовлень не дає дублів / пропусків.
- [ ] Номер однаковий у таблиці, чеку, трекінгу та push.
- [ ] Міграція безпечна на наявній БД.
